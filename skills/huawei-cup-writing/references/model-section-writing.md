# Model Section Writing

Normative rules: `DEPTH-001`, `STRUCT-001`–`STRUCT-003`, `CLAIM-002`, `TERM-002`, `NUM-001`–`NUM-004`.

## Input Boundary

只使用已经给出的模型、公式、代码映射、参数和求解证据。本文件不负责选择或升级模型。

## Construction Order

1. 说明题目特征为什么需要当前模型关系；至少指出一个题面中的目标、数据结构、约束条件或时空特征，以及它在模型中的具体落点。只写一段可以替换到多数题目的模型简介，不足以说明模型选择；
2. 定义变量、集合、参数、单位和来源；关键参数还要交代其数值来源、推导或标定方式，以及它在模型中的作用；
3. 在给出核心公式前说明公式要表达的对象和进入当前问题的原因，公式后说明符号、关系和输出含义；基础定义不必套用同等篇幅，但不能让核心方程脱离语境；
4. 逐类说明关键约束的现实含义；
5. 写清已实际采用的求解方法和必要设置；
6. 说明输出如何回答本问并进入后续结果；若声称与其他子问题存在承接，必须指出实际传递的变量、参数、结果、约束或模型输出，以及后续环节如何使用它；
7. 只引用已经完成的验证、对比或敏感性证据。

空间位置、方向、角度和几何关系不能只放入符号表；已有示意图时应与图中标注和正文说明保持同一符号语义。

## Model responsibility checks

写入一个主要模型、算法或处理模块前，先从冻结事实中确认以下关系：

1. 它解决当前问题中的哪个明确困难；
2. 它接收什么输入，产生什么输出；
3. 它在前后模块之间承担什么接口作用；
4. 若删去它，模型链会失去什么能力；
5. 它是否承担对照、验证或解释职责，而不是只出现在算法名单中。

上述关系必须来自 Project Facts、代码映射或已提供的模型证据。材料无法确认时，登记事实缺口，不自行补写选择理由；不能因为模型或算法数量较多就默认存在问题。

## Context and provenance checks

- **模型定制性**：逐段检查“题目特征 → 模型关系 → 预期输出”的链条。若删去题目名称后段落仍可原样用于许多无关问题，应补充具体映射，而不是增加“合理、有效、综合”等评价词。
- **跨问承接**：不要把“先解决第一问，再解决第二问”当作模型关联。只有能定位前一问的输出和后一问的输入或约束时，才写成“基于前一问结果”；否则分别说明两问的独立关系。
- **参数溯源**：对影响目标函数、约束、阈值或最终选型的参数，至少保留“参数值—单位—来源或推导—模型作用”四项信息。缺少来源时提出证据缺口，不凭常识补值。
- **公式语境**：核心公式前后各承担一个清晰任务：前文交代建模对象和用途，后文解释变量与关系。不要用连续公式堆叠替代模型逻辑，也不要把公式含义全部推给符号表。

## Formula-to-decision continuity

公式解释不能停在变量流水账。给出公式前，先说明它处理的是哪个题目关系、为什么需要该关系；给出公式后，至少交代关键变量如何共同决定目标、约束或评价结果，以及计算输出将用于哪个方案比较、分配、筛选或后续问题。标准公式的理论含义只写材料能够支持的部分，不为增加深度补入未经核实的性质或机理。

“不引入主观赋权”这类方法辩护句不应代替方法动机。若事实允许，改为“为利用当前样本的差异信息确定指标相对权重，在标准化结果基础上采用熵权法计算权重”，并保持其适用范围。

## Independent module wording

当两个问题没有模型接口时，优先分别写明各自的输入、处理对象、输出和解释用途。这样可以自然呈现独立性，避免连续使用“不使用、不调用、不依赖、不提供”等否定式接口句。只有需要排除一个具体且容易产生的误读时，才保留一处必要的否定说明。题目尚未给出求解结果时，写模型的待求输出或求解目标，不把“尚未求解”“仍待计算”等工作状态写成正文结论。
