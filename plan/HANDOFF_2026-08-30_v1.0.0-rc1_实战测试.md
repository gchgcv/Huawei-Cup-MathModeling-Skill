## 7. 已确定的中文写作规则

中文学术表达不应照搬英语长句的信息压缩方式。

每句话优先承载一个主要判断。观察、证据、解释、条件和适用范围可以拆开表达。不要为了提高信息密度，把多个逻辑层级塞进同一个长句。

段末也不要机械使用“未通过、未包含、未完成、未验证”等防御型句式。应说明当前结果能够支持什么，以及后续判断需要什么证据。

已批准示例：

> 当前结果反映模型在内部交叉验证下的表现，外部泛化能力还需在独立样本上进一步检验。

## 9. 实战中的缺口分类

发现问题后，不要立即扩写 Skill。先归类：

1. `SKILL_GAP`：稳定、可复用的能力缺失。
2. `CONTRACT_GAP`：模块之间缺少明确输入输出。
3. `TOOLING_GAP`：需要确定性脚本、validator 或 runner。
4. `EVIDENCE_GAP`：缺少数据、日志或人工评价。
5. `EXECUTION_ERROR`：本次操作失误，不应写入长期规则。
6. `CASE_SPECIFIC`：只适用于当前题目，不应泛化。

只有前 3 类经过复现后，才考虑进入后续 Skill 修订。

## 10. 实战证据要求

每个准备沉淀为 Skill 的问题至少应记录：

- 触发场景；
- 原始输入；
- 实际输出；
- 期望输出；
- 可复现步骤；
- 影响范围；
- 临时修复；
- 是否具有跨题复用价值；
- 应归属的模块；
- 对应 regression test。

不要根据单个案例直接建立庞大规则。优先解决能够复现、影响明确的问题。

一次实战回合至少应得到：

- 结果、图表与论文内容之间能够相互追溯；
- Writing / Review 的真实表现记录；
- false positive、false negative 或 fidelity 问题记录；
